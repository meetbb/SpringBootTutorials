# Development Log — 2026-09-27

## What we worked on today

- **Checkpoint 8 — Refresh Token Flow**: `JwtService` now generates a second token type — a refresh token, same shape as the access token but longer-lived and tagged with a `type: refresh` claim so it can't be used as an access token (or vice versa; `JwtAuthFilter` now rejects a refresh token presented as a Bearer access token). Added the `RefreshToken` entity/table (Postgres) storing a SHA-256 hash of the token, the user id, and expiry — never the raw token. `login()` now issues and persists both tokens; `LoginResponse` returns both. Added `POST /auth/refresh`: validates the JWT's signature/expiry/type, then confirms its hash is still known to the server via a DB lookup before issuing a new access token.
- **Checkpoint 9 — Logout / Token Revocation**: Added `POST /auth/logout`, which validates the refresh token the same way `/auth/refresh` does, then deletes its row via `RefreshTokenRepository.deleteByTokenHash`. Deleting the row is what makes `/auth/refresh` reject the token afterwards, even though the JWT itself would otherwise still parse as valid until its natural 7-day expiry. Logout is idempotent — an unknown or already-deleted token is a no-op, not an error.
  - Bug found and fixed during live testing: `logout()` initially had no `@Transactional`, and the derived delete query failed at the persistence layer (`TransactionRequiredException`) because JPA's `remove` needs an active transaction. Added `@Transactional` to `UserService.logout()`.
- **Checkpoint 10 — Centralized Exception Handling**: Added `ErrorResponse` DTO (`timestamp`, `status`, `message`) and a `GlobalExceptionHandler` (`@RestControllerAdvice`) mapping `InvalidCredentialsException`/`InvalidRefreshTokenException` → 401, `EmailAlreadyExistsException` → 409, `UserNotFoundException` → 404, `@Valid` failures (`MethodArgumentNotValidException`) → 400 with field errors joined into one message, and a catch-all `Exception` → 500 with a generic message (never leaks the exception's class name or internal message). This fixes the known rough edge from Checkpoints 3–7: a `@RestControllerAdvice` intercepts the exception inside the original request, so Spring never forwards to `/error` — which our security rules were blocking and turning into an empty `403`.
- Added unit tests for all of the above: `UserServiceRefreshTest`, `UserServiceLogoutTest`, `GlobalExceptionHandlerTest`, plus updates to `JwtServiceTest` and `UserServiceLoginTest` for the new constructors and return shapes.
- Fixed a pre-existing flaky test: `JwtServiceTest.isTokenValid_returnsFalse_forTamperedToken` tampered the token's *last* character, which sometimes falls on unused base64url padding bits and doesn't actually change the decoded signature — occasionally the tamper went undetected. Fixed by tampering a middle character instead. Verified stable across 15 repeated runs.
- Live-tested the full flow end-to-end via Docker (Postgres + Redis) and `spring-boot:run`: register → login (both tokens) → refresh → logout (204) → refresh again (401, correctly rejected) → logout again (204, idempotent) → duplicate email (409) → wrong password (401) → blank password (400) — all returning clean JSON instead of the old empty-403 behavior.

## Decisions made

- Refresh tokens are a second JWT (reusing `JwtService`), not an opaque random string — simpler to build for a learning project, distinguished from access tokens via a `type` claim.
- The refresh token's hash (SHA-256, not BCrypt) is stored in Postgres — deterministic hashing is required for a `WHERE tokenHash = ?` lookup, unlike BCrypt's randomized salt.
- Logout deletes the DB row rather than soft-deleting/marking revoked — reuses the exact "hash not found" rejection path `/auth/refresh` already has, no schema change needed.
- Skipped the optional access-token blacklist (Redis) for Checkpoint 9 — a stolen access token still naturally expires within 15 minutes, and adding Redis-backed revocation wasn't judged worth the complexity for this project's scope right now.
- Error response status codes: went with the more precise 404/409 over collapsing everything into {400, 401, 403} as the design doc loosely suggested — standard REST practice, no added complexity.

## Known remaining gap (not fixed, noted on purpose)

`GlobalExceptionHandler` only catches exceptions thrown inside a controller method. An expired/invalid **access token** hitting a protected endpoint (e.g. `/auth/me`) is rejected by Spring Security's filter chain itself, before the controller/advice ever runs — that path still returns a bare `403` with no JSON body. Fixing it would need a custom `AuthenticationEntryPoint`/`AccessDeniedHandler`. Out of scope for what was asked in Checkpoint 10 — left for a future checkpoint if it becomes relevant.
